# Boss Helper 开发经验

在修改本扩展前，先阅读 `docs/浏览器插件产品与工程交接方案.md`，并在扩展仓库根目录执行只读的 `git status --short`。该仓库是 `Extension/boss-helper`，而不是外层 Jobjob 工作区；保留已有未提交改动，避免使用 `git add .`、重置或清理工作树。

## 先确定修改所在链路

按下面的入口定位，而不是从 UI 文案直接猜测：

- BOSS 页面数据和详情读取：`src/entrypoints/boss/index.ts`。
- BOSS 请求与外部打招呼：`src/entrypoints/boss/requests.ts`。
- 筛选、AI 调用与任务依赖：`src/composables/useApplying/`。
- AI 模型配置和 Prompt 渲染：`src/composables/useModel/`、`src/composables/conf/`。
- AI 决策契约：`src/services/jobMatching.ts`。
- 飞书鉴权、查重和写入：`src/services/feishu.ts`。
- 飞书字段 URL 数据形状：`src/services/feishuFields.ts`。
- 后台跨域请求：`src/message/background.ts`。

功能变更若跨越这些边界，先写出实际数据从哪里来、在哪里校验、在哪里产生外部副作用，再动手。不要为未来的多模型、多数据源或任务恢复预建没有调用方的框架。

## 必须保持的产品边界

- 岗位采集、AI 筛选、飞书同步和 BOSS 打招呼/投递必须独立控制。
- AI 异常、配置缺失、飞书写入失败或字段不匹配时，不能降级为继续投递。
- `REJECT` 永不自动投递；`REVIEW` 只有在自动投递和 REVIEW 投递两个开关都开启时才允许投递；`APPLY` 仍要求自动投递开关开启。
- 飞书同步成功、BOSS 请求成功和用户完成正式求职申请是不同层级的事实，日志、UI 和交付说明不得混为一谈。
- 不替用户提交申请、接受邀约或发送站外消息。真实 BOSS/飞书操作仅在用户明确授权且小范围验证后进行。

## BOSS 数据经验

本插件复用用户已登录 BOSS 页面中的 Vue 状态与点击后的详情，不应把类型注释、旧字段名或页面文字当成已验证的实时数据源。

- 需要新增字段时，先从脱敏的真实列表/详情样本确认字段存在、类型、空值和岗位 ID 对应关系；再写入类型、快照和飞书映射。
- 招聘者“今日活跃”等信息不能当作岗位发布时间或岗位更新时间。没有稳定原始来源时，字段应留空或不写，不允许用 `Date.now()` 伪造来源时间。
- 详情读取依赖页面点击和异步状态，修改时覆盖“列表切换、详情超时、岗位 ID 不一致、字段缺失”场景，防止旧详情写入新岗位。
- BOSS 页面结构和接口会变；页面可见不代表可稳定采集。优先补脱敏 fixture 和明确的失败提示，不做静默猜测。

## AI 简历匹配经验

简历只保存在扩展本地配置中，但匹配时会发送给用户选择的模型服务。明确告知这一数据流，不记录简历内容或模型 Key。

- Prompt 可以引导 JSON，但安全边界是本地的严格解析与 schema 校验。
- 变更模型调用或 AI SDK 版本时，分别验证最终可读文本、结构化输出对象和流式错误路径；不要假定某个 `text` 或 `output` 字段在所有 Provider 中相同。
- 输出契约、默认 Prompt、解析器和投递决策必须同步改动并覆盖合法/非法输出测试。
- 不把模型推测写成候选人事实；缺口和未知项应保留为 `gaps`、`uncertainties`，而不是通过提示词抹掉。

## 飞书多维表格经验

`BOSS 岗位 ID` 是当前 upsert 主键。它决定查找、创建和更新，不要改用岗位名称、公司名称或 URL。

- 飞书字段名与字段类型是 API 契约。修改任意列前，同步核对 `fieldNames`、快照构造、字段格式化、README/交接文档和测试。
- 先区分权限问题、字段不存在、字段类型不匹配和 URL 数据形状不匹配。不要把 `URLFieldConvFail` 或 `FieldNameNotFound` 归因为泛泛的“飞书连不上”。
- 用户维护的求职进度属于用户数据：初次创建可设默认值，后续同步不得覆盖。
- 同步时间是本次同步发生时刻；不能替代 BOSS 岗位更新时间。
- 鉴权、查重、创建和更新应在可注入的请求适配器下写测试；真实 App Secret、app token、table ID 不进 fixture、日志或仓库。

## 配置、隐私与权限

- 模型 Key、飞书 App Secret、Cookie、`bst`、Authorization 头和完整第三方响应均不得输出到控制台、任务日志、测试夹具、README 或提交记录。
- 扩展配置导出可能包含敏感数据。涉及导入/导出时优先增加脱敏和显式确认，而不是默认把完整配置写文件。
- 当前的广泛 host permission 是动态模型 Base URL 和飞书访问的风险点。任何扩大权限或新接第三方服务前，先评估数据范围和用户授权。

## 验证与交付

按改动风险组合验证，至少报告验证层级：

1. 纯逻辑：AI JSON 解析、投递许可、字段格式化和错误翻译的单测。
2. 服务契约：飞书鉴权、按岗位 ID 查重、创建、更新、字段错误的 mock 请求测试。
3. 构建：优先运行 `./node_modules/.bin/wxt build -b chrome`。
4. 浏览器：手动加载 `.output/chrome-mv3`，检查设置、BOSS 页面数据读取和任务状态。
5. 外部验收：仅在授权后，以小范围 BOSS/飞书测试确认真实字段、记录更新和投递控制。

当前 `vue-tsc` 在既有 TypeScript/Node 组合下可能因 `./lib/tsc` exports 兼容性失败。不要把这种环境失败写成新改动通过或失败；先记录它，再以可运行的构建和定向测试补证。构建通过同样不等同于扩展已发布、飞书已成功写入或用户已验收。

完成后，提供改动文件、验证命令与结果、尚未验证边界。提交、推送、合并、发布和用户验收必须分别说明。
