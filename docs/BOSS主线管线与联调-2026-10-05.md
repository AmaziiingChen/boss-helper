# BOSS 主线管线与联调

## 当前范围

BOSS 列表 → 飞书已有岗位查重 → 新岗位完整详情 → 按当前筛选翻页 → 简历与个人资料匹配 → 飞书去重入库 → 单条进度回读 → 招呼语生成、编辑和明确确认后单条发送。

附件简历发送、自动批量投递、猎聘与前程无忧不进入本轮主线。历史模块保留，不扩展。

## 操作与恢复

- 在 BOSS 原站设置关键词和筛选，打开扩展的原生 Side Panel。
- 在“简历”页导入/编辑简历，导入 `profile/matching-profile.json`，点击保存；个人资料是匹配与招呼语共用的补充背景。
- 在 AI 设置中保存 `API Key + Base URL + Model`；在飞书设置中保存现有岗位表配置并检查连接。
- 开始采集会处理当前页并翻页；采集流程本身只获取、分析、入库。
- 工作台“AI 自动分析”开关自动保存，任务运行中不可切换。关闭后直接采集并写入飞书，新岗位的五个 AI 字段写空值；单条更新已有记录时同样写空值；开启后按已保存简历和模型配置执行匹配。切换后再次采集会保留详情，重新分析或跳过分析并同步飞书；关闭期间修改简历或模型不会触发重复入库。
- 批量采集先用列表中的 BOSS 岗位 ID 查询飞书，已有记录标为“飞书已有，已跳过”，不打开详情、不分析、不写入，也不等待岗位请求间隔。单条“更新分析与入库”允许处理已跳过记录；当前会话已获取详情的岗位仍可复用详情重做分析或入库。
- 采集的岗位间隔至少以 5 秒为基准、翻页至少以 15 秒为基准，配置更长时沿用配置，每次独立浮动 ±20%。每批最多获取 20 个详情，随后暂停并等待手动继续。详情错误、超时、可识别的原站验证/频繁访问提示、飞书查重失败都会暂停；完成原站验证或稍后确认后再继续。分批与间隔降低持续请求量，不保证不会触发平台验证。
- 每个岗位显示详情、分析、入库的独立状态；入库失败后重试不会重复获取详情或调用已成功的分析。
- 保存了新的简历、个人资料、提示词、模型名称或服务地址后，下一次开始/单条更新会重做分析和入库，保留详情。改飞书目标表只重做入库。
- 无输入变化时，“更新分析与入库”复用成功阶段；它不是强制重新调用模型的按钮。
- 已成功或结果不确定的发送记录不随资料更新清除；不会因重新分析重复联系招聘人。
- 飞书按 BOSS 岗位 ID 查找后更新/新建。遇到远端同 ID 多条记录会报错，保留已有求职进度。
- 岗位详情内“回读进度”只读取该岗位当前飞书记录；发送前也会重新回读，必须为唯一的“待处理”记录。
- 招呼语可以编辑并保存本地。确认窗口绑定当前岗位、招聘人和精确正文；资料变化后旧草稿失效，需要重新生成。
- 首次页面绑定失败后可随面板轮询重试；重复绑定保留原站 getter/setter，避免叠加通知。

## 提示词与评测

默认匹配规则区分硬性资格、可迁移能力、工作意愿和实际职责。实习/应届岗位允许学习空间；不以 Agent 接入或 AI 字样直接推荐，不将做过的项目自动兑换成兴趣。当前方向优先于旧简历目标标题；仅有通用能力关联、偏离当前主线的岗位列为备选 REVIEW。理由、匹配点、缺口与待核实项保持简短，已明确排除的资格不再追问能否破例。

升级仅替换完全一致的旧默认提示词，用户编辑过的提示词保持原样。个人资料会额外加入分析输入，不依赖自定义提示词是否写了对应占位符。模型日志只保留调用状态，不记录完整简历、个人资料或 SDK 请求事件。

9 个场景位于 `tests/evaluation/matching-cases.json`。离线检查：

```sh
npm run eval:matching
```

经用户授权后，设置 `MATCHING_BASE_URL`、`MATCHING_API_KEY`、`MATCHING_MODEL`，用以下入口运行真实模型评测：

```sh
npm run eval:matching -- --live --resume /绝对路径/简历.md
```

真实评测会发送指定简历、个人资料和模拟 JD。结果保存在项目根目录 `.local/matching-evaluation/`，不进入仓库。决策标签匹配仅供回归参考，需要人工检查理由、缺口和职业意愿；不能据此声称模型具有某个准确率。
