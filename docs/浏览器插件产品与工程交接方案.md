# BOSS 求职助手浏览器插件产品与工程交接方案

## 1. 文档用途

本方案面向接手开发的产品负责人、前端/扩展开发者和集成开发者。它说明本插件的来源、当前产品目标、代码入口、BOSS 数据链路、AI 简历匹配、飞书多维表格同步、配置与安全边界、当前完成度，以及下一阶段的开发顺序。

接手后应先把本文件中的“当前未提交功能”整理为可测试、可提交的最小变更集，再继续新增能力。不得把本文件中的“代码已存在”表述为“已在真实 BOSS 页面和飞书生产环境验收”。

## 2. 一页结论

插件当前是一个运行在 BOSS 直聘网页内的 Chrome MV3 扩展。它复用 BOSS 网页自身的列表和详情数据，以筛选工作流逐个处理岗位；当前正在叠加三项本地优先能力：

1. 导入或粘贴 Markdown 简历，并调用用户自行配置的 OpenAI-compatible 模型，输出严格的 `REJECT`、`REVIEW` 或 `APPLY` 决策。
2. 将岗位和 AI 结论以 BOSS 岗位 ID 为主键写入飞书多维表格；同步与实际打招呼/投递是两个独立开关。
3. 对自动投递采用默认关闭、AI 输出不合法即停止、`REJECT` 永不投递的失败关闭策略。

当前最大的工程事实是：这些新增能力仍处于未提交工作树状态。Chrome 构建已在本机通过；完整 TypeScript 检查受当前 `typescript`、`vue-tsc` 和 Node 运行时兼容性阻塞；真实 BOSS → AI → 飞书 → 投递闭环尚未形成可复查的通过证据。

## 3. 范围与非目标

### 3.1 本阶段目标

- 在用户已登录的 BOSS 直聘网页内读取岗位列表和点击后的详情。
- 对每个符合基础筛选条件的岗位运行 AI 简历匹配。
- 将岗位信息、AI 结论和用户在飞书维护的求职进度集中到一个飞书多维表格。
- 仅在用户明确开启自动投递时，调用 BOSS 网页已有的打招呼/投递请求。
- 保持用户的简历、AI Key 和飞书凭证只在本机扩展配置中使用，避免写入仓库、日志和交接材料。

### 3.2 明确不在本阶段范围内

- 不提交职位申请表、不接受邀约、不向招聘方发送邮件或站外消息。
- 不绕过登录、验证码、访问控制、频率限制或 BOSS 平台限制。
- 不把 AI 结论、飞书写入成功或页面点击成功表述为真实录用、投递成功或业务结果。
- 不把招聘者活跃度冒充为岗位发布时间/更新时间。
- 不新增多数据源、云端账号系统、多模型路由或复杂任务恢复，直到当前闭环验收完成。

## 5. 产品流程与状态边界

```text
用户已登录 BOSS 网页
        |
        v
读取页面 Vue 状态中的岗位列表
        |
        v
基础筛选（公司、职位、薪资、地址、猎头等）
        |
        v
点击岗位并读取详情
        |
        +--> AI 简历匹配关闭：不调用模型，AI 状态为 NOT_RUN
        |
        +--> AI 简历匹配开启：发送本地简历文本 + 岗位信息给用户选择的模型
                                    |
                                    v
                      严格校验 REJECT / REVIEW / APPLY JSON
                                    |
        v                           v
飞书同步开启 ----------------> 按 BOSS 岗位 ID 创建或更新飞书记录
        |
        v
自动投递开启且决策允许？
        |
   否 -- 结束，不调用 BOSS 打招呼请求
        |
   是
        v
调用 BOSS 页面已有打招呼/投递请求
        |
        v
若飞书同步开启，再次 upsert 记录（用于刷新同步时间）
```

这里“同步成功”“BOSS 请求返回成功”和“用户真正完成求职投递”是不同证据层。开发日志和 UI 文案必须保持这个区分。

## 6. BOSS 数据获取与页面依赖

### 6.1 当前实现方式

插件不是独立爬虫，也没有 BOSS 官方 API。`src/entrypoints/boss/index.ts` 通过 Vue hook 读取 BOSS 页面组件中的 `jobList`、`pageVo`、`hasMore` 和 `jobDetail` 等状态，并在需要完整 JD 时模拟/触发岗位卡片点击，等待详情状态出现。

列表阶段得到 `BossZpJobItemData`；详情阶段得到 `BossZpDetailData`。飞书快照优先使用详情中的岗位地址、完整 JD、技能、公司规模/行业/融资阶段、招聘者姓名/头衔与岗位状态；缺失时再使用列表值。

### 6.2 BOSS 请求

| 用途         | 代码                         | 主要接口/行为                                                      |
| ------------ | ---------------------------- | ------------------------------------------------------------------ |
| 岗位详情     | `requests.ts#getJobDetail`   | `GET /wapi/zpgeek/job/detail.json`，需当前页面 Cookie 中的 `bst`   |
| BOSS 信息    | `requests.ts#getBossData`    | `POST /wapi/zpchat/geek/getBossData`                               |
| 打招呼/投递  | `requests.ts#sendPublishReq` | `POST /wapi/zpgeek/friend/add.json`，带 `securityId` 与加密岗位 ID |
| 页面数据监听 | `index.ts`                   | 不直接伪造列表请求，复用登录态页面已有数据                         |

### 6.3 已确认的限制

- 页面 Vue 状态、DOM 结构和接口字段都可能随 BOSS 更新而变化；任何版本升级后先做真实页面回归。
- 当前采集证据中没有稳定、可验证的“岗位发布时间”或“岗位更新时间”。因此该飞书字段已从当前增量代码中移除。
- `今日活跃`、`昨日活跃` 等是招聘者活跃信息，不能写入岗位时间列。
- 详情获取依赖页面点击与最长 60 秒等待；页面改版、懒加载或列表切换都可能造成读取失败或串位，需增加岗位 ID 一致性测试。

## 7. AI 简历匹配

### 7.1 用户体验与配置

在“AI 配置”页的 `JobMatchingSettings.vue` 中，用户可以：

- 选择 `.md`/`.markdown`/文本简历，或直接粘贴 Markdown 简历；文件只读取为文本，内容保存在扩展本地配置。
- 选择已有模型配置。模型包含 Base URL、API Key、模型名等，支持 OpenAI-compatible 服务。
- 开关“开启自动投递”和“REVIEW 也投递”。两者默认均关闭。
- 开关飞书同步并填写飞书应用配置。

### 7.2 输入与输出契约

默认 Prompt 位于 `src/composables/conf/info.ts`。模型输入由模板渲染得到，包括：候选人简历、岗位名称、薪资、学历/经验、福利、公司与招聘者信息、地址和完整 JD。

模型只能返回以下 JSON 对象，字段不能多、不能少：

```json
{
  "decision": "REJECT|REVIEW|APPLY",
  "reason": "总体判断理由",
  "matchPoints": ["有简历依据的匹配点"],
  "gaps": ["缺口、风险或硬性冲突"],
  "uncertainties": ["待核实项"]
}
```

`parseJobMatchResult` 会拒绝空输出、非 JSON、字段增减、未知决策、空理由和包含非文本成员的数组。即使上游模型没有可靠 JSON mode，本地校验仍是实际安全边界。

### 7.3 投递许可矩阵

| AI 决策           | 自动投递关闭 | 自动投递开启且 REVIEW 开关关闭 | 自动投递开启且 REVIEW 开关开启 |
| ----------------- | ------------ | ------------------------------ | ------------------------------ |
| `REJECT`          | 不投递       | 不投递                         | 不投递                         |
| `REVIEW`          | 不投递       | 不投递                         | 可投递                         |
| `APPLY`           | 不投递       | 可投递                         | 可投递                         |
| 输出无效/调用失败 | 停止         | 停止                           | 停止                           |

注意：飞书同步与自动投递独立。AI 匹配关闭时，若飞书同步开启，现实现仍可能创建 `AI 决策 = NOT_RUN` 的岗位记录；但不会发送 BOSS 投递请求。

### 7.4 隐私边界

简历文本会发送给用户选择的 AI Provider；岗位内容也会发送给同一 Provider。当前配置和简历文本保存在浏览器扩展 Storage 中，并非加密保险箱。配置导出功能可能包含 App Secret 和模型 API Key，禁止将导出的配置 JSON 放入 Git、聊天记录、截图或共享网盘。

## 8. 飞书多维表格集成

### 8.1 前置条件

用户需要在飞书开放平台创建或使用一个自建应用，并在应用权限中开通 `bitable:app` 多维表格读写权限、发布新版本、把应用加入目标多维表格。仅 `readonly` 权限不足以创建或更新记录。

扩展本地需要配置：

- `appId`：飞书应用 App ID。
- `appSecret`：飞书应用 App Secret，必须只留在用户本机。
- `appToken`：目标多维表格 app token。
- `tableId`：目标数据表 table ID。

### 8.2 调用顺序与幂等规则

`src/services/feishu.ts` 的 `upsertJobToFeishu` 依序执行：

1. 请求 `POST /open-apis/auth/v3/tenant_access_token/internal` 获取 tenant access token。
2. 在内存缓存 token，过期前 5 分钟重新获取。
3. `POST /bitable/v1/apps/{appToken}/tables/{tableId}/records/search`，以 `BOSS 岗位 ID` 精确查找记录。
4. 找到记录则 `PUT /records/{recordId}`；找不到则 `POST /records` 创建。
5. 仅创建时写入 `求职进度 = 待处理`；后续同步不覆盖用户在飞书维护的求职进度。

岗位 ID 使用 BOSS 的 `encryptJobId`。这是当前唯一的 upsert 主键；不要改成岗位名称、公司名称或链接，因为它们并不稳定或不唯一。

### 8.3 当前字段契约

下表是 `fieldNames` 的代码事实。飞书列名须完全一致；不同类型必须按对应说明创建。

| 飞书字段                              | 建议类型                              | 写入来源/规则                                        |
| ------------------------------------- | ------------------------------------- | ---------------------------------------------------- |
| BOSS 岗位 ID                          | 单行文本                              | `encryptJobId`，upsert 主键                          |
| 岗位名称                              | 超链接                                | `{ text, link }`，显示岗位名并链接 BOSS 详情页       |
| 公司名称                              | 单行文本                              | BOSS 公司名                                          |
| 公司链接                              | 超链接或与当前适配形状兼容的 URL 字段 | 显示公司名并链接公司页                               |
| 薪资                                  | 单行文本                              | BOSS 原始薪资描述                                    |
| 薪资下限（月）、薪资上限（月）        | 数字                                  | 仅可解析 `10-15K` 类月薪时写入，单位为元             |
| 实习周期                              | 单行文本                              | 每周天数与最短月数，缺失可为空                       |
| 城市、区县、商圈、详细地址            | 单行文本                              | 详情优先，列表兜底                                   |
| 学历要求、经验要求                    | 单选/文本                             | 当前会归一化为有限中文值；若用单选，选项须覆盖代码值 |
| 职位技能、岗位标签                    | 多选/文本                             | 当前写字符串数组；字段类型须能接收数组               |
| 公司规模、公司行业、融资阶段          | 单选/文本                             | 规模/融资阶段会归一化，未知为 `未知`                 |
| 招聘者、岗位状态                      | 单行文本/单选                         | 招聘者由姓名与职衔合成；状态默认 `正常`              |
| 完整 JD                               | 多行文本                              | 详情岗位描述                                         |
| AI 决策                               | 单选/文本                             | `REJECT`、`REVIEW`、`APPLY` 或 `NOT_RUN`             |
| AI 判断理由                           | 多行文本                              | AI `reason`                                          |
| AI 匹配点、AI 缺口与风险、AI 待核实项 | 多行文本                              | 每项以 `• ` 换行保存                                 |
| 求职进度                              | 单选/文本                             | 仅初次创建写 `待处理`，后续由用户维护                |
| 同步时间                              | 日期时间                              | 当前同步的 Unix 毫秒时间戳                           |

已移除且不应重新加回的字段：`工作性质`、`招聘者活跃度`、`岗位更新时间`、`是否已沟通`、`是否已投递`、`招聘者在线`、`招聘者已认证`、`金牌猎头`、`申请类别`。其中岗位更新时间没有可信 BOSS 来源；其余字段已按当前产品取舍不再由代码写入。

### 8.4 飞书错误定位

| 现象/错误码         | 首先检查                                                           |
| ------------------- | ------------------------------------------------------------------ |
| `99991672`          | 应用是否已开通并发布 `bitable:app`，并被添加到目标 Base            |
| `1254068`           | `岗位名称` 是否仍是超链接类型，且接受 `{link, text}`               |
| `1254060`           | 文本字段是否被改成了不兼容的字段类型                               |
| `1254064`           | `同步时间` 是否为日期时间字段，并接受毫秒时间戳                    |
| `URLFieldConvFail`  | 逐项核对 URL 列类型与飞书当前接口要求；不要把错误吞掉或改写为成功  |
| `FieldNameNotFound` | 飞书列名与 `fieldNames` 是否完全一致；删除字段前先同步删除代码映射 |

飞书写入失败会中断当前岗位任务，因此在当前实现中不会继续调用 BOSS 投递请求。这是刻意保留的失败关闭行为。

## 9. 配置、权限与安全要求

### 9.1 扩展权限

`wxt.config.ts` 当前声明：

- `storage`：保存配置、预设、简历文本。
- `notifications`：任务通知。
- `host_permissions: ['http://*/*', 'https://*/*']`：允许用户配置的 AI Provider、飞书和既有 BOSS 请求跨域访问。
- BOSS 内容脚本匹配 `zhipin.com` 及其子域。

全域 host permission 是当前灵活接入 OpenAI-compatible Base URL 的代价，也是最需要审视的权限。下一位开发者不能在未评估影响的情况下扩大权限，更不能以此读取无关站点数据。

### 9.2 禁止项

- 不在 `console.log`、任务日志、错误对象、测试夹具或 README 中输出 App Secret、API Key、Cookie、`bst`、Authorization 头或完整飞书响应。
- 不把浏览器 Local Storage 当成服务端密钥管理。
- 不复制用户真实 BOSS 页面 HTML、真实简历和带身份信息的截图到仓库。
- 不以 API/模型/飞书异常为由绕过 AI 判断而直接投递。

### 9.3 现有防护与缺口

- 已做：后台请求日志仅记录 URL 和方法/状态，不再直接打印请求配置或完整 Response。
- 已做：飞书超链接字段仅允许 `http:` 与 `https:` URL。
- 已做：AI 输出本地严格校验，异常会停止。
- 待做：配置导出前默认遮蔽密钥，或提供显式“含敏感配置导出”确认。
- 待做：对飞书写入 payload 增加脱敏调试模式和可重放的非敏感 fixture。
- 待做：复核 `host_permissions` 是否可收窄为 BOSS、飞书和用户确认的模型域名白名单。

## 11. 推荐开发顺序

### P0：先让当前闭环可验证

1. 为 `parseJobMatchResult` 和 `shouldDeliverJob` 写独立单测：合法 JSON、围栏 JSON、字段缺失/多余、错误决策、空数组、自动投递矩阵。
2. 为飞书服务注入 `fetch` 或后台请求适配器，写请求级单测：鉴权、按 ID 查询、创建、更新、token 缓存、字段映射、错误码翻译。
3. 建立不含真实姓名、岗位、URL、Cookie 和凭证的 BOSS 列表与详情 fixture；验证列表 → 详情 → 飞书快照不串岗位。
4. 在用户明确允许的真实飞书 Base 中，用一个人工可识别的测试岗位验证创建、第二次更新、求职进度不被覆盖、链接显示和时间格式。
5. 在浏览器手动加载 `.output/chrome-mv3`，在 BOSS 已登录的测试页面逐个验证：AI 关闭、AI 无效 JSON、REJECT、REVIEW、APPLY、飞书关闭、飞书失败、自动投递关闭。

### P1：修复当前产品可靠性

1. 修复/固定 TypeScript 与 `vue-tsc` 的兼容组合，使 `npm run check` 成为可重复的门禁。
2. 把飞书字段名与类型做成可见的“连接检查”页面：先读元数据，缺字段或类型不兼容时给出具体差异，不进入投递工作流。
3. 将飞书写入拆为“入库”和“投递后状态更新”两个明确动作，避免同步失败/重复同步的状态歧义。
4. 增加单条岗位的可读审计记录：采集来源、AI 决策、飞书 record ID、是否调用 BOSS 请求、失败阶段；严禁记录密钥和 Cookie。
5. 删除 README 中失效字段，补充安装、开发、测试和飞书字段契约。

### P2：在 P0/P1 验收后再考虑

- 多份简历/岗位目标的选择机制。
- 由用户主动触发的批量复评和飞书状态回读。
- 多招聘来源适配器。
- 本地加密、密钥导出控制、细化 host permission。
- 更精确的 BOSS 页面变更检测与降级提示。

## 13. 交接验收标准

下一位开发者可以宣布“当前闭环已可用”的最低条件是：

- Chrome 构建和稳定的类型/单测门禁均通过。
- 至少一个脱敏 BOSS fixture 覆盖列表、详情和字段空缺场景。
- AI 无效输出在测试中证明确实阻止投递。
- 飞书创建、更新、重复 upsert、链接字段、求职进度保留和字段不匹配错误均有可复查测试。
- 用户授权的真实 BOSS/飞书小范围验收完成，并明确记录：测试日期、测试岗位数量、飞书 record ID（可脱敏）、是否真正调用投递，以及未覆盖的边界。
- 当前工作树已提交到明确分支；推送、合并、发布和用户验收分别记录，不互相替代。

## 14. 维护原则

这个插件的核心不是“尽可能多地自动打招呼”，而是让岗位采集、AI 判断、飞书记录和外部动作可分开控制、可追溯、可停止。任何新增自动化都必须先保留这条边界。
